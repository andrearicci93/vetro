# Q74T Remote PC integration

This branch adds an opt-in `remote-pc` platform adapter. It can work with the
owner's separately installed boot supervisor and renews its authenticated
channel every 15 minutes. The WGT does not install or replace a persistence
hook, modify a raw block device or change accounts.

The default build remains diagnostics-only. `VETRO_REMOTE_PC_MODE=manual`
enables explicit dashboard actions and the adapter's package operations.
`restoreInput` resumes explicitly saved remote interception; `restorePreferences`
restores the saved launcher, DNS and Quick Wins choices once root is ready.
Neither flag starts MQTT or changes the service's boot flags. Waiting for root
consumes no restore attempts, and transient boot failures are retried serially.
Root-channel renewal is independent of these feature restores. `automatic`
also enables the remaining upstream restore behavior. Diagnostics stays read-only.
With no enabled physical rule and saved input preference, no input helper starts.

## Observed on hardware

The owner's Q74T runs Tizen 5.5 / Node 4.4.3 on ARMv7. The standard integration's
`/usr/bin/dotnet` entry point is absent. These are device observations, not a
claim about all Tizen 5.5 televisions.

The stock runtime serves Vetro's dashboard and the new adapter. Direct unsigned
JavaScript and shell entry files are rejected by the firmware. Inline Node
module loading and shell sourcing work in the tested SDK context; neither
requires changing firmware enforcement. Node's child-process implementation
aborted in the SDK-context test. The TV successfully executed `id` through the
separate shell executor using its original interpreters and inline loading.

The Remote PC adapter and a fresh command through its authenticated channel
were demonstrated on the Q74T / T-NKMDEUC-2743.0 on 2026-11-02. The Node agent
and its shell command reported UID/GID 0, `CapEff=0000003fffffffff` and
`System::Privileged`. The command completed with exit 0, without a timeout or
stderr. Vetro's system monitor also returned a fresh memory snapshot after the
Mac's VNC and SMB laboratory services had been stopped.

The first demonstration used an unpacked SDK-context service. A subsequent
owner-signed widget installation (test 2) was also verified: the service runs
as UID 5001, its loopback-authenticated agent runs as UID/GID 0 with the same
capabilities and label, and its system monitor completes root-backed reads.
The widget's local diagnostic report includes 415 apps and all ten checks.
Root stays connected after stopping the Mac's VNC/SMB laboratory services.

The initial signed diagnostic installation recorded `onboot=false` and
`autorestart=false`. That test did not prove cold-boot recovery. A subsequent
owner-supplied handoff reports persistent root and automatic agent connection
across multiple real power cycles using an external boot hook and supervisor.
This code update does not independently reproduce that hardware test and does
not install or alter those working persistence files.

The public
[Q60T persistence implementation](https://github.com/sebastianspicker/tiz0wn/tree/main/exploits/tiz0wn-root)
uses a raw block modification of a profile carrier. Its offsets and device
assumptions must not be reused for another model. No such persistence installer
is packaged here. Existing persistence should be left in place when updating
the widget.

## Design

- The adapter starts Vetro's existing loopback-only `SAMSUNG-TV-ROOT/1` server.
- A fresh owner-writable staging directory contains readable code and a private
  mode-0600 one-use 32-byte secret. Status exposes a setup username, never the
  secret. The root runtime itself is root-owned and mode 0700.
- An already installed boot supervisor picks up fresh staging directories.
  Without one, setup requires Remote PC and the authenticated SMB laboratory.
  No automatic Remote PC trigger or boot-supervisor installer is implemented.
- The setup username contains no whitespace: the firmware splits credential
  words and joins them with commas before evaluating them. The stdin bootstrap
  survives that transformation; an earlier `. /path` prototype did not.
- The privileged supervisor creates a root-owned mode-0700 runtime. The Node
  agent verifies ownership and permissions before using the shell executor.
- Authenticated commands use strictly increasing sequence numbers, a 64 KiB
  command limit, a 120-second timeout ceiling, bounded output and a queue limit.
- The shell runs commands in separate sessions. Timeout and disconnect terminate
  their process groups. Private command files are removed after each result.
- The launch script invokes the shell worker by content, since indirect script
  paths are rejected by this firmware. It loads narrowly scoped SMACK rules
  between the root label and the service's own validated label before connecting.
- The supervisor cleans its runtime when the agent exits. The adapter renews
  its staging directory and secret at the deadline. An in-flight command may
  fail at renewal and is never automatically retried.
- Package installation uses `vd_appinstall` through the authenticated root
  channel. A successful submission is not reported as a verified installation;
  disconnection or timeout after dispatch leaves the outcome unknown.
- `setApplicationsEnabled` uses the existing owner-UID package commands and
  protection for Smart Hub/Vetro. The HTTP Debloater retains its separate
  single-component `--global` change, registry readback and restore behavior.

The physical-input helper is separately compiled for .NET Core 3.0 in
`rooting/payload55`. Remote PC packages select that DLL and runtime config; the
archive integration retains its original payload. The builder verifies the
compiled helper against its source and binary hashes before packaging it.

On this Q74T, `dotnet-launcher --standalone` can run the helper from Vetro's
installed app directory. It refuses an assembly staged in `/tmp`, and the SDK
share path is not visible after the launcher enters its .NET zone. A detached
child shell sets only its own label to `System::Privileged` before invoking the
launcher. No global SMACK rule or boot file is changed by this input launch.
The runtime preserves UID/GID 0 but clears effective capabilities; device access
and filtering were therefore verified directly rather than inferred from root.

Hardware verification on 2026-11-03 used a temporary, self-expiring harness with
the same service socket label and authenticated input bridge. Four candidates
connected in observe mode. The owner pressed volume keys: events came from
`Smart Control 2016` with codes 68 (up) and 67 (down). A separate filter test
blocked only code 68 and forwarded code 67; both the event frames and the owner
confirmed the result. Closing the bridge stopped the temporary filter. No saved
shortcut or app setting was changed by these tests. An app-launch shortcut in
the final signed widget still requires the owner's installation and test.

That test also exposed Node 4's inherited `Buffer.from` rejecting arrays, not
only strings. The compatibility shim now copies array/Buffer inputs explicitly;
otherwise authentication failed at the zero-byte HMAC separator before any key
could be captured.

The Q74T launcher is separately compiled for .NET Core 3.0 in `rooting/dock55`.
It invokes Samsung's `dotnet-launcher --standalone` with a child-only
`System::Privileged` label. A runtime preflight precedes catalog writes, starting
the process or changing Home/Autorun. Its pid, FIFO, log and catalog live in
Vetro's app shared directory: Samsung drops capabilities, and `/home/owner` is
0750 on this TV. Home, navigation and launching an installed app were confirmed
by the owner on 2026-11-03. The final startup/probe/stop code was also tested on
hardware. The standard integration retains its .NET 3.1 launcher.

On the Q74T, HbbTV's service is marked autorestart, and Ambient is restarted by
screend. Tizen 5.5 Quick Wins use reversible `pkgcmd --global` activation for
these two exact app IDs, with saved previous state, readback and rollback.
HbbTV keeps its menu value and brake-file handling. Ambient is fully disabled,
including manual launch, until the option is undone. The screen daemon is left
running. Both disable/enable round trips were verified on the owner's TV.
Multi View uses `/tmp/multiview_disable_preloading` on this firmware; its old
persistent Vetro marker now records the choice and the real flag is restored
at service startup. Its systemd preload unit is stopped before the app.

The hosts filter was present and resolving blocked names to zero in the system,
Home, YouTube, HbbTV and Ambient mount namespaces. Status additionally checks
one configured domain through the system IPv4 resolver. This does not establish
that app caches or private resolvers are filtered, and does not block arbitrary
subdomains or every advertisement. A final signed-widget cold-boot verification
remains outstanding for all restored preferences. The
ordinary HTTP dashboard retains its upstream trusted-LAN access model.

## Build

```sh
VETRO_ROOT_METHOD=remote-pc VETRO_PORT=9000 node rooting/build.cjs
```

The integration builder still needs the owner's signing certificates. For a
temporary unpacked SDK test, this produces the same diagnostic sources plus an
explicitly unsigned WGT:

```sh
VETRO_PORT=9000 node rooting/tools/build-q74t-prototype.cjs
```

For the first feature test, build the manual package on port 9000:

```sh
VETRO_PORT=9000 VETRO_REMOTE_PC_MODE=manual node rooting/tools/build-q74t-prototype.cjs rooting/dist/q74t-manual
```

The owner signs and installs the resulting `q74t-manual-unsigned.wgt` using
Apps2Samsung. The `config.xml` service entry loads `service/main.js`; the
separate `q74t-prototype-start.js` is only for temporary SDK diagnostics and
continues to enforce read-only HTTP and its 15-minute service limit.

To rebuild the experimental input payload, use an existing SDK compiler and
the target firmware's existing .NET Core 3.0 assembly directory. The script
does not download or redistribute firmware assemblies:

```sh
python3 rooting/tools/build-input-tizen55.py --dotnet /path/to/dotnet --compiler /path/to/Roslyn/bincore/csc.dll --references /path/to/3.0.0 --out rooting/payload55
```

An unsigned WGT needs signing before installation. `q74t-prototype.py --help`
documents temporary staging, status collection and process-verified shutdown.
Its device addresses and reviewed SDB helper are explicit caller arguments.
Keep reports, synthetic credentials and deployment records outside the repo.

`q74t-remote-pc-lab.py` reuses the owner's existing reviewed laboratory without
changing its current-run pointer. Prepare a fresh run using a captured status,
then run its SMB self-test with the existing SMB virtual environment. Only
`start` needs sudo: it binds port 445, drops back to the invoking user and then
starts the bounded synthetic VNC and read-only SMB services.

## Validation

When installing a new signed widget, verify the saved preferences on hardware:

1. Confirm the existing supervisor reconnects the agent after installing and
   opening the widget. Leave the persistence files in place.
2. In Task manager, select one nonessential removable user app whose current
   flag is enabled. Disable it, confirm readback, then re-enable it and confirm
   the original flag. Do not start with an assistant/tracking group.
3. Separately try enabling the Launcher. If .NET is unavailable, stop there;
   leave Home unchanged and inspect the reported error. Otherwise confirm the dock
   appears, Home/Back work, and turning it off restores the prior behavior.
4. In Remapper, use automatic detection while listening, press the desired key,
   save one app shortcut and explicitly enable interception. Listening picks the
   node that actually emits the key; choosing the first `Smart Control` entry
   can select an idle device. Saved and enabled interception reconnects by itself.
5. Keep `manual` until these checks succeed. A working root connection alone
   does not validate the Launcher, remapper or all firmware settings.

```sh
node rooting/tests/run.cjs
VETRO_ROOT_METHOD=remote-pc node rooting/tests/node4-syntax.test.cjs
node app/tests/run.cjs
python3 .github/scripts/test_parse_log.py
python3 .github/scripts/audit_release.py
```

The agent tests deliberately use a simulated root identity on the host. They
verify protocol interoperability, invalid MACs, replay rejection, output and
timeout bounds, cancellation, private staging and package selection. They do
not attest root on a television. The shell-executor tests run actual host shell
commands; the separate SDK-context hardware check establishes that execution
path on the owner's TV.

AI-assisted implementation; hardware limitations and unverified behavior are
stated separately from passing host fixtures.

Rebuild the Tizen 5.5 launcher with existing compiler and firmware assemblies:

```sh
python3 rooting/tools/build-dock-tizen55.py --dotnet /path/to/dotnet --compiler /path/to/csc.dll --references /path/to/3.0.0 --out rooting/dock55
```

The builder checks source and DLL hashes; no firmware assemblies are packaged.

## Follow-up audit on the installed widget

The installed `b46f924` build was checked through its dashboard APIs. Inventory,
startup listing, telemetry, settings reads, native menu catalog, privacy, Home
order, remote configuration, DNS and Quick Wins returned data. Reading the
cleanup list did not delete any installed package or leftover file.

Picture writes and restoration succeeded for panel brightness, contrast,
sharpness, color and HDMI black level. Local dimming, blur reduction, judder
reduction and LED Clear Motion failed the write/readback check in the tested
source/mode. They remain readable but are now blocked from writes on the Q74T
until a device retest establishes their parameters and conditions. A rejected
write now checks whether the original value already remains before retrying
restoration; a setter error alone does not prove rollback failure.

Follow-up fixes prepared offline:

* Decode counted ConnMan replies on systemd 231, which lacks busctl JSON output.
  This fallback was checked against the owner's TV before it became unavailable.
* Retain the launcher's generated catalog in service memory when package-label
  permissions prevent direct dashboard reads of the root-written file.
* Kill the remaining HbbTV UI process after its service is disabled; its graceful
  termination had left the app running on the installed widget.
* Package a .NET 3.0 audio/source reader, using a private temporary JSON file
  because Samsung redirects managed stdout. The standard 3.1 payload is preserved.

Pending hardware checks: the new signed widget, full cold boot and standby,
launcher preview under the installed package label, final HbbTV stop behavior,
and native audio/source output. MQTT/Home Assistant needs a configured broker.
Uninstall, file cleanup and wholesale voice/tracking group changes were not
exercised merely for the audit. This audit does not establish every feature as
working on the Q74T.

## Boot supervisor PID reuse fix

A subsequent cold-boot failure was traced to the external hook's persistent
`/opt/tvroot/supervisor.pid`: its stored number belonged to `security-manage`
in the new boot. The hook's `kill -0` succeeded for this unrelated process and
skipped launching the supervisor. The root agent therefore never connected,
including when the owner reinstalled an earlier WGT. Another full restart
restored the root channel and allowed a backed-up correction.

The one-line fix uses `PIDFILE="$LOCK/supervisor.pid"` inside the existing
root-owned `/tmp/.q74t-boot-lock` directory. This directory is recreated on
cold boot, so a PID from a previous boot cannot suppress startup. The raw
profile carrier and the supervisor body are unchanged.

`tools/fix-q74t-boot-pid.py` prepares a **local** copy only, refuses unexpected
hooks and never contacts a TV. It is not bundled in the WGT. Before applying
an external-hook update, save and verify its original hash/permissions, back
it up, and replace only the writable `/opt/tvroot/boot` atomically. The owner
must separately validate a complete restart. `tests/boot-pid.test.cjs`
reproduces the live-but-unrelated PID and tests the corrected guard.

The one-line correction was applied to the owner's existing writable boot
hook with a verified backup, original-hash check and atomic replacement.
After a further owner-performed full restart on 2026-11-03, the new PID file
identified a root-owned `sh` supervisor and the dashboard reported the agent
connected as UID/GID 0 with its expected capabilities. The corrected hook's
hash matched after restart. No WGT replacement, raw carrier write or account
change was needed for this recovery. The running widget remained the owner's
reinstalled `b46f924` build, confirming this boot defect was independent of
the later feature-audit widget changes.
