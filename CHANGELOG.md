# Changelog

## 0.4.0 — Security & Plugin update (unreleased)

The theme of this release: Vetro is closed to other people on your network (sign-in), opens up to add-ons (plugins), and stops more of what the TV sends out (ads and privacy).

- **Dashboard and API sign-in** ([#5](https://github.com/andrearicci93/vetro/issues/5)): unpaired LAN clients are refused. A browser or script pairs once with a 6-digit code that only the TV shows (the Vetro app displays it) and receives a random key, sent as an `HttpOnly`, `SameSite=Strict` cookie or `Authorization: Bearer`. Only key hashes are stored. Browser requests whose `Origin` does not match the host are refused, including pairing itself (cross-site requests); the no-key bypass for TV apps needs an IP or `localhost` host (DNS rebinding), while paired devices may use any host name; only one pairing runs at a time and wrong codes are limited. At most 20 devices can be paired (a 21st gets a clear error); key-file read or write failures are logged and reported to the pairing device. The TV widget on loopback and app-only mode need no pairing. `app/scripts` send `VETRO_TOKEN`. See [sign-in](app/docs/SIGN-IN.md). Written by zerodevb ([#9](https://github.com/andrearicci93/vetro/pull/9)). The sign-in code appears in the dashboard card of the TV screen with the name of the browser that asked, and plugin pages get a session limited to their own routes.
- **Quick settings and Startup now work together.** Turning a Quick settings group off disables its components and also clears *Start at boot* and *Restart automatically* on them, so a disabled component no longer sits in the Task manager Startup list with its flags still on. The previous flag values are kept on the TV (`/home/owner/share/vetro/quick-flags/<app>`) and put back when you turn the group on again; if that fails, the dashboard names the components to check. A group whose components are all disabled but some still start at boot or restart reads *Partly done · N still start at boot or restart* and turning it off again finishes the job. If the flags cannot be cleared, the whole change is rolled back. Both views read the same app list, so a change in one shows in the other at once, the component page in the Startup tab says which Quick settings switch covers it, and the Startup list is reloaded after a Quick settings change. Not tried on a TV: the flag clearing and restore run as a root script against the package database, like the Startup toggles.
- **Pairing survives a reload.** If you reloaded the sign-in page while a code was on the TV screen, the new page had lost the pairing id: the code on the TV could not be confirmed and *Show a code* answered that a pairing was in progress, until the code expired two minutes later and a fresh one worked. The browser that asked for the code now keeps a short-lived `vetro_pair` cookie (2 minutes, `HttpOnly`, `SameSite=Strict`, path `/auth`); after a reload the page offers the code field again, and a different browser is told another device is pairing and for how long. A waiting code is still never replaced. The TV screen shows how long the code stays valid and removes it when that time is up, even if the service stops answering.
- **Advertising list: the canary ad configuration host.** `rtb-config-canary.samsungads.com` is named by the ad agent (`adagent-service`) as well as by the ad framework and Samsung TV Plus, next to `rtb-config.samsungads.com` which was already listed. It is in the firmware strings; whether the TV asks for it, and what happens when it is blocked, was not tested.
- **Plugins (API 1, experimental):** add-ons written by other people. A plugin is a folder or a single `.vplugin` text file with a manifest and an entry file; it is installed from the dashboard (a public list read from GitHub in the browser, or a file), lands switched off, and its code is not even read until you switch it on. Plugins can add a page to the sidebar (sandboxed frame, with a session limited to that plugin) and ask for the `exec` permission, which the dashboard shows before you install. The host guards every call, switches off a plugin that keeps failing, and starts the next boot in safe mode if one did not finish (plugins stay listed so the culprit can be switched off or removed). Updates come from the dashboard: a plugin with a newer version in the list shows *Update*, which turns it off, replaces it, keeps its saved settings and turns it on again, unless the new version asks for different permissions. A written warning says that plugins are third-party code, spot-checked and not audited, with no guarantee and no responsibility on the author of Vetro. Developer tools: `scripts/vetro-plugin.cjs new|check|pack|index` and a guide in `docs/plugins.md`. This is fault isolation, not a security sandbox. Checked on a test server with a fake list; not tried on a TV.
- **Diagnostic export: component details (opt-in).** The Diagnostics panel has a new switch, *Include details about unrecognised components*. On, the report adds what the package manifests of the components Vetro has no description for declare: description, privileges, whether they ask to start at boot and whether the TV registered that (`differs`), and SHA-256 checksums of the manifest and of the programs that start at boot. It makes reports from other TVs comparable (the same checksum on two TVs is the same program) and would have shown the #25 and #26 startup problem at a glance. Off by default; a few hundred small files read in small steps at the lowest priority, stopping after about a minute. On the Q80A, with 220 packages, it took 3 s, the longest single read was 0.4 s, and other root commands waited at most 0.2 s. No paths, addresses, URLs or author names. The community report check (`parse_log.py`) now knows the `launcher`, `quickWins` and `components` sections and lists components whose start flags differ from their manifest.
- **Diagnostic export: firmware and Tizen version read by the service.** Two of the last four community reports (#17, #25) had no model and no firmware, because those values come from a probe the Vetro page has to post. The service now reads the firmware (`/etc/prd_info.ini`) and the Tizen version (`/etc/tizen-release`) itself and says where each came from (`firmwareSource`, `tizenVersion`). The commercial model still needs the probe.
- **Version in the sidebar:** the footer under the app count and the connection state now says which Vetro build is running (*Vetro 0.4.0*), read from the service's `/status`.
- **Stop Ambient now holds.** On the Q80A, `screend` (Samsung's screen daemon) started `org.tizen.ambientapp` again within 2–7 s of any stop, so 0.3.0 could only offer a partial block. `ambient_app_enable=0` and `app_disable=true` in the package registry do not change that. What does: stop `screend`, kill the app, start `screend` again. `screend` does not launch the app by itself when it starts (only Samsung's `ambient_start.sh` does, at boot), so it stays off: it was still off after several minutes, and a launch made the way `ambient_start.sh` makes it was caught and ended within seconds. After each restart Vetro waits for that script to launch the app and ends it the same way. Checked on a Q80A with a real restart on 2026-10-25: Ambient was not running 337 s after the TV came back, with `screend` active and the picture normal. The win is now called **Stop Ambient** (no longer "partial block"). Opening Ambient yourself still works, and `screend` starts it again after you close it until the next stop.
- **Stop viewing-data collection (new quick win):** stops `contents-recognition-service` (recognises the app, content type and channel on screen), `canalysis`, `pisa-service` and `adagent-service` (analytics and ads), `mirroring-recognition-manager`, `contents-ui-detector-service` and `contents-ott-detector-service` (find thumbnails and app screens in the picture; the second is started by the recogniser, not by a unit), `kpi-logging` (key presses), `emergency-log-transmitter` and `devicetracker`, now and again after every restart. `canalysis` and `pisa-service` are held off across restarts by the files their own start-up units check (`/opt/usr/share/systemd/system/canalysis-daemon` and `pisa-service`; the second also covers `adagent-service`); the others are stopped at each boot, twice, 45 s apart, because some start late. `data-service`, which collects KPI logs (its configuration lists remote keys, apps, channels, volume and the advertising ID as sources; its log endpoints are on `lcprd1.samsungcloudsolution.net`, which is the address the TV was connected to; what it sends is encrypted and was not inspected), is started again over D-Bus by other components; the win adds that host to the saved list of the domain filter, and says *Uploads can resume* until **Block ad and tracking domains** is on. If the filter is off, it is not switched on for you. Switching off starts the services again and removes the host if Vetro added it. Tried on a Q80A on 2026-10-25: a restart brought back every service that has no brake file, which is why the boot step exists. With the boot step installed, a second restart left all eight stopped from the first reading (112 s after boot) to the last (376 s); only `data-service` ran, as expected, and the second pass at about 170 s changed nothing visible. Some features that report back to Samsung, such as targeted suggestions, may stop updating. `canalysis` also works on logo recognition for HDMI inputs and `pisa-service` starts feature services and handles ad terms, so source recognition or some consent screens may change; neither was tested.

## 0.3.5 — 2026-10-29

- **Select the TV tuner directly** ([#31](https://github.com/andrearicci93/vetro/pull/31), by tomcraft): `KEY_TV` and `XF86DiscretSourceTV` are now accepted by the native key control and by remapping actions, so a rule such as "back to live TV" can select the tuner instead of cycling through the sources. Checked by the author from an HDMI source and from a foreground app; whether the key exists is firmware-dependent, and on a TV without it the request does nothing.
- **Remote interception finds the remote again after Linux renumbers its inputs** ([#32](https://github.com/andrearicci93/vetro/pull/32), by tomcraft): a saved `/dev/input/eventN` is not a stable identity, and a remote that shows several interfaces under one name stayed disconnected after a restart or a reconnection. With several same-name interfaces, Vetro now picks the one that advertises keys (read from sysfs); if two or more do, it keeps the saved one when it is among them; if it cannot decide it leaves interception off instead of guessing. Replayed on five cases and checked by the author on a TV for the automatic reconnection; a real renumbering was not provoked.
- **The service can run on Node 4.4 (Tizen 4 and 5.5), app-only** ([#33](https://github.com/andrearicci93/vetro/pull/33), by SalustLab; issues #2 and #19): those TVs run the web service on Node.js 4.4.3, not Node 12, and the service stopped twice, while loading (`async` functions, `fs.promises`) and on the first request (`Promise.prototype.finally`, `Buffer.alloc`, `Buffer.from` with a string). A new `compat.js` adds the three missing built-ins only where they are absent, and the package reader is written with promise chains. Nothing changes on a runtime that has them. Tested by the author on a QN55Q80TAGXZD (2020, Tizen 5.5): the dashboard, the app list, the diagnostics and the start after a cold boot work, 45 requests ran without a crash. This is the app-only package: **no root** on that platform (no `/usr/bin/dotnet`, .NET Core 3.0, no mount namespaces), so the features that need root are not available. Not tried on a Tizen 4 TV.
- **Advertising list: two more components** ([#44](https://github.com/andrearicci93/vetro/pull/44)): `com.samsung.tv.iacr` and `com.samsung.tv.screen-analysis-dbmgr` are now listed as advertising in the Debloater and as tracking in the app catalog, instead of "other". Nothing is turned off by itself: each one is still disabled by hand, one at a time. Covered by the test suite and tried on a Q80A.
- **Home order on The Frame 2024 (Tizen 8.0)** ([#45](https://github.com/andrearicci93/vetro/pull/45); issue [#41](https://github.com/andrearicci93/vetro/issues/41), reported by Nyar-cloud): on firmware T-PTMDDEUC-1400.1 the Home order file ends with `EOFCOBA` (no space), and reading it failed with *Home order terminator missing*. Both `EOFC OBA` and `EOFCOBA` are now accepted, and the one found is written back unchanged when the order is saved. Covered by the test suite; not tried on a TV. The second problem in #41 (`csfs` coming back after pressing Home) is not fixed.
- **Dashboard: app ID shown when app names repeat** ([#52](https://github.com/andrearicci93/vetro/pull/52), by domenix): entries with the same name in the app pickers are different apps or menus; the app ID is now shown next to the name so they can be told apart.
- **TV screen redesign:** Vetro's screen on the TV shows its state more clearly, with a diagnostics panel and the app icon. While checking, it says what it is doing, and every check has a time limit so the screen no longer hangs on "Checking". The web dashboard is unchanged.
- **Installation guide** ([#39](https://github.com/andrearicci93/vetro/issues/39), by bertrandom): where the TV's DUID is shown, that `tizen install` should be used and `sdb install` can do nothing without an error, where the Tizen Studio tools usually are, and `sdb shell 0 vd_applist` to check that the installation reached the TV.
- **Installation guide: where to get Tizen Studio** ([#47](https://github.com/andrearicci93/vetro/pull/47), by bertrandom): Samsung's Tizen Studio page now redirects to its VS Code extension, so the guide links to the Tizen Studio installer directly.
- **Installation guide: open Vetro once after installing** ([#49](https://github.com/andrearicci93/vetro/pull/49); issue [#25](https://github.com/andrearicci93/vetro/issues/25), reported by JamesMills818): on some TVs the installer registers the service without on-boot and auto-restart. Since 0.3.2 Vetro sets them back, but only after the app has been opened once, so the install steps now say so. Documentation only.
- **Troubleshooting: "TV platform adapter unavailable"** ([#42](https://github.com/andrearicci93/vetro/pull/42)): the message means the package was built without the root integration (app-only); the fix is rebuilding with `node build.cjs` in `rooting/` (installation step 3).
- **Compatibility:** a Samsung Q80R QN65Q80RAFXZA (2019, Tizen 5.0, firmware T-MSMAKUC-1500.5) works with a personal port ([#35](https://github.com/andrearicci93/vetro/issues/35), by torresdrew): its own launcher host (.NET Core 2.1.4), the older app registry and icon layout, and Node.js 16.20.2. It is not the stock package and the changes are not merged; it is listed as working with local changes.
- **Compatibility:** a Samsung S90D QA65S90DAULXL (2024, Tizen 9, firmware T-PTMDUABC-0090-2130.0) on Vetro 0.3.2 ([#36](https://github.com/andrearicci93/vetro/issues/36), by Inderdeep29): service on Node v18.18.2 and the UID-0 root agent running, the Launcher on with 15 apps and no error, and, in the owner's account, the root agent back after a full restart.
- **Compatibility:** a Samsung The Frame QN75LS03BAFXZA (2022, firmware T-PTMAKUC-1720.7) on Vetro 0.3.2 ([#39](https://github.com/andrearicci93/vetro/issues/39), by bertrandom): service on Node v12.16.3 and the UID-0 root agent running; after the Host PC IP was set to `127.0.0.1` the service started by itself after a cold boot. The Launcher was not tried.

## 0.3.2 — 2026-10-26

- **Vetro starts at boot on TVs whose installer ignored the package's request** ([#29](https://github.com/andrearicci93/vetro/pull/29), by domenix; issues #4, #25 and #26): on an S90C (Tizen 7.0, firmware T-PTMCDEUC-2000.2) three clean installs registered `vetrotvapp.svc` with `app_onboot=false` and `app_autorestart=false`, although `config.xml` asks for `true` for both, so the service did not start after a restart (not within 3 minutes) until someone opened the app. The same registration shows in the reports for the QE55QN93AATXXC (#26) and the GU75CU7179 (#17). Once the root agent is connected, Vetro now puts those two flags back for its own service, once per service start and only when one is off, with the same backup-and-read-back write the Task manager uses. Checked on the S90C: started 40 to 65 s after a restart or a power cut. Nothing else is touched, and the Task manager still refuses to change Vetro's own flags. The root agent has to connect first, so a new install still needs the app opened once.
- **Community report check:** it now knows the `launcher` and `quickWins` sections (every comment since 0.3.0 said *plus 2 unrecognised*), and it reads the `firmwareSource`, `tizenVersion` and `components` fields that the next minor release adds, so reports from it are not flagged.
- **Correction to 0.3.1:** its notes said the Home cache moved on *2022* TVs. TVs with the new Home (`com.samsung.tv.home.media`, `home.sidebar`, `coba.newhome`) include 2022 models on Tizen 6.5 and models up to 2025 on Tizen 9 (pull requests [#20](https://github.com/andrearicci93/vetro/pull/20) and [#23](https://github.com/andrearicci93/vetro/pull/23)). The fix is the same one. On Tizen 9 the Launcher still closes only `com.samsung.tv.csfs`, so the memory it frees may be smaller than on the Q80A.
- **Compatibility:** the S90C row now has its model (TQ65S90CATXXC, 2023) and firmware ([#27](https://github.com/andrearicci93/vetro/pull/27), by domenix). The README credits Apps2Samsung for the install-leftovers cleanup ([#21](https://github.com/andrearicci93/vetro/pull/21), by PatrickSt1991).

## 0.3.0 — 2026-10-25

- **Port clash** (issue #16): the port is no longer fixed at 8099. `VETRO_PORT=9000 node build.cjs` (in `app/` or `rooting/`) writes the port into the widget's access origin, the probe page and the service, so Vetro can sit beside an app that already uses 8099 (tizen-youtube). The default and the default package are unchanged; a port outside 1024–65535, or 8001/8002 (used by the TV's remote sockets), is refused. It is a build-time choice, not a setting on the TV. Not tried on a TV.
- **Installation guide** (issues #11 and #12): a short version at the top (the two packages, what you do and what you do not do), the TV's *Host PC IP → 127.0.0.1* step as its own step 5, and a table for "root agent not connected" that starts from what `/status` shows.
- **Quick settings, privacy curated:** the separate *Privacy* section is gone. Its *ACR viewing data* switch only covered components that **Disable all advertising and tracking** already switches off, so it was a duplicate; the domain filter now sits under *Advertising and tracking*.
- **Launcher, Fix TizenTube:** the switch is greyed out, with the chip *TizenTube is not installed on this TV*, once the app list has been read and TizenTube is not in it (an already-on switch can still be turned off).
- **Diagnostic export:** two new sections, `launcher` (on, running, Samsung’s Home running, Fix TizenTube, Autorun Smart Hub switched off, counts, whether a TizenTube tile exists; never the log, error text or app names) and `quickWins` (auto update, MultiScreen, Ambient). 16 sections in all.
- **Staging folders:** each service start left a new `archive-root-<id>` folder and signed archive in the TV's staging folder (150+ after a few weeks, about 10 MB on a nearly full `/opt`). The service now keeps the current one and the two newest, skips a folder that appears on a running process’s command line (checked in tests only, not yet seen on the TV), and removes the rest and the archives without a folder. Reaches the TV with the next signed build.
- **Launcher (new tab):** a glass launcher for the Home key (`dock/`, a .NET process run by the TV's own `dotnet`). Turning it on, after an in-page warning, builds its app list from Samsung's own Home row (row order, registry titles and registry icons, read from the TV each time it starts), starts it, and closes Samsung's Home; Settings and Source in the launcher still open Samsung's screens. Nothing is disabled or removed: if the launcher stops, the Home key goes back to Samsung's Home, and Vetro starts the launcher again after a restart or a crash (backing off up to five minutes between tries and never switching itself off, starting it the moment the root helper connects, from the list saved by the last start). Turning the launcher on also switches off Samsung's *Autorun Smart Hub* setting (`db/menu/smart_hub/ontvsetting/auto_start`), so the TV no longer powers on to Samsung's Home; Vetro remembers the old value and puts it back only if it changed it, when the launcher is turned off. Tested on a Q80A only; experimental on other models. While it is on, the tab shows a preview of how the launcher looks on the TV. **Fix TizenTube** (a switch in the same tab) gives the TizenTube tile the YouTube icon and closes Samsung's YouTube (`com.samsung.tv.cobalt-yt`) just before TizenTube starts.
- **Dashboard redesign:** the dashboard now follows the Vetro design system (`app/design-system`: tokens, a reference page and `DESIGN.md`), shows the Vetro icon (served at `/icon.png`) and has a new first group in the navigation: **Quick settings**, **Launcher** (marked Beta) and **Remapper** (the former Remote panel). The Debloater is now **Task manager**. A test keeps the page's tokens identical to `tokens.css`.
- **Quick settings are quick wins:** every switch is worded as the win it gives and *on* means it is applied, with a chip saying *Done* or *Partly done* and a short "What this changes" note. New: **Disable HbbTV** (see below), **Disable MultiScreen autostart** and **Disable automatic firmware update** (`db/menu/support/softwareupdate/autoupdate` 1 → 0 with read-back and rollback; the value that was there is kept and restored on switch-off). Memory figures (HbbTV about 22 MB, Multi View about 15 MB) come from a process survey of a Q80A; the effect of each change on a running TV is not yet verified.
- **HbbTV:** the menu value Off does not stop HbbTV on the Q80A: the app keeps running, and `hbbtv_service` (which listens for app status changes) starts it again at boot, on a source change and when the TV wakes. Tried on the Q80A on 2026-10-23: stopping the app, even with `-k` and with the firmware's own brake file `/tmp/hbbtv_do-not-relaunch` in place, brought it back within 2–4 s; stopping `hbbtv_service` first and then the app kept it off for the 40 s that were watched, and the service did not restart by itself. Off now means the menu value 19, the brake file, the service stopped and the app stopped, in that order, and Vetro does it again after every restart of the TV. Off never starts anything; On removes the two flag files and starts the service and the app. A menu value of Off with the app or its service still running is shown as *Partly done*. Not yet checked: standby and wake, a cold boot, and the red-button deeplink from the TV viewer, which may start the app by another route.
- **MultiScreen:** the TV starts it at boot with a Samsung unit that skips itself when `.../com.samsung.tv.multiscreen/data/disable_preloading` exists; the win creates that file (owned by the app's group) and stops the app, and Multi View still starts on demand. Verified on the Q80A on 2026-10-23: systemd reports the start condition as not met and does not loop. The choices are saved in `vetro-quick-wins.json` in the share folder.
- **Ambient (partial block):** stopping AmbientApp with `-t` or `-k` does not last on the Q80A: it is back within 2–6 s. The process that does it is `screend`, Samsung's screen daemon (the app's launch record names its PID as the caller). `screend` keeps a list of apps to start again when they end, and puts `org.tizen.ambientapp` on it only when the model has the read-only firmware feature `com.samsung/featureconf/ambient_screen_support`; the only built-in brake is a flag it sets while the TV powers off. Neither of its two Ambient settings (`ambient_app_enable`, `ambient_setting`) changes this. So there is no complete block: **Stop Ambient (partial block)** stops the app now and after each restart of the TV (about 59 MB), and says in the dashboard that Samsung may start it again. The disable flag stays unused, because `ambient_start.sh` would retry forever at the next boot. Found by reading the Q80A `screend` binary; the effect on a running TV has only been timed with the stop commands.
- **Quick settings, two all-in switches:** **Disable all advertising and tracking** and **Disable all voice assistants**, each in its own section. Their members are whatever the Task manager files under Advertising and tracking or Voice assistants on the TV, except components with the role *Keep* (Smart Hub's ad agent, which Home loads) and Vetro itself; the list is shown under the switch. They use the same disable flag and rollback as the other groups and stop members that are running. The voice switch asks for confirmation: it also turns off the remote's microphone button, Voice Guide (read-aloud) and voice suggestions in search. The existing per-feature switches (viewing data, Alexa, Bixby, …) stay and show the same state.
- **Domain filter candidates:** `osb.samsungqbe.com`, `rm.samsungqbe.com` and `scs.samsungqbe.com` (found in the firmware, usage unknown) and, labelled *unverified*, `gpm.samsungqbe.com` (a guess at where the viewing-data service learns its servers). `svdca.samsungqbe.com`, which Certificate Manager needs, is on the never-block list.
- **Launcher look:** a new look, chosen in the designer page (`dock/designer`): a solid bar, smaller icons, a thin light line inside every icon, a white focus ring and a glow in the colour of the selected app (ring, glow and icons share one corner radius), the selected icon rising a little, two outline pills (Settings, Samsung Home), a “Source” hint, no name labels or clock, a cascade entrance and constant-speed focus movement. The preview in the Launcher tab follows it.
- **Diagnostics read from seven community reports:** two things had never worked outside the Q80A. The SoC temperature was empty in every report, because Samsung's TVs have no Linux thermal zones; Vetro now reads the driver's own file (`/sys/devices/platform/soc/*thermal/temperature`, whole degrees), which also fills the MQTT temperature sensor. And the CPU rate was empty in four of seven, because its second sample waited behind the slow startup listing in the TV's one-at-a-time command queue; the other reads now start after it.
- **Startup listing no longer times out on slower TVs:** it was one command that needed 13–17 s of `systemctl list-unit-files` work on a Q80A, against a 15 s limit, and the Diagnostics `startup` section came back *unavailable: command timed out* in the QN55Q65, Q65S95C and QN55S95B reports. The running states and the boot states are now two commands (the second with a 60 s limit); if the second fails, the listing still shows what runs, with the boot state unknown. The report gives this section a longer deadline.
- **Compatibility:** community report from a Samsung QN55Q65DAGXZS (2024, firmware T-NKLDUABC-0090-2123.9) on Vetro 0.2.3 (issue #10): built unsigned and loaded with apps2samsung, reported working; the export shows an authenticated UID-0 agent, the service running on Node v18.18.2 and 29 confirmed controls. Cold-boot persistence was not reported.

None has been written on a TV by the maintainer. Each is editable only after the TV's own `busctl introspect` lists the exact method and signature; otherwise the row stays read-only with the reason, and a failed check never touches the six controls verified earlier. Writes keep the read-back and rollback of the existing controls. The method list is fetched once per service run. The diagnostic export now records, for every control, whether the TV exposes it (`confirmed`, `missing`, `signature-mismatch`) and how many methods it offers, so a report from another model shows which controls it supports.
