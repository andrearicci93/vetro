# Changelog

## 0.7.2 — unreleased

### Home Assistant (MQTT)

- **A Power state sensor.** Home Assistant shows On while the TV's picture is on and Standby when it is off (Picture Off, or the TV's own standby), as an On / Standby choice you can use in automations ([#304](https://github.com/andrearicci93/vetro/pull/304) by [bmfurtado](https://github.com/bmfurtado)). It is read with the same short command as the volume and the input (one more setting, no program started), and it is unavailable on a TV where that setting cannot be read. Tried only in unit tests so far; the Q80A reads 1 with the picture on and 3 with Picture Off.
- **Change channel from Home Assistant, a script or a voice assistant.** Vetro listens on `<prefix>/<identity>/channel/set`: send a channel number (`31`, or `{"channel": 31}`) and the TV goes there. With Vetro's tuner running and Samsung's live TV on screen it tunes at once; otherwise Vetro sends the digits as the remote would and Samsung's own TV app does the rest. Home Assistant gets a **Tune channel** number box by itself. Only digits 1 to 9999 are accepted, retained messages are ignored, and it shares the 500 ms limit of the MQTT rules. It does not turn the TV on. See `app/docs/mqtt/README.md` for the Alexa setup.

- **HDMI Source Images: a PC, a Blu-ray player or a box without a recognised picture gets Samsung's picture for its type** ([#297](https://github.com/andrearicci93/vetro/issues/297)). For an input the user set to a device type, Samsung's list names an SVG, which the launcher cannot draw (the TV's picture library has no SVG loader on any firmware), so the tile kept Vetro's own icon. The same picture exists in Samsung's resources as a PNG (2020 to 2024 TVs) or a WebP (2025 Tizen 9 and Tizen 10) under the same name, and the tile now takes the one that exists. A device Samsung recognises keeps its own picture, which wins; the TV input and the ports without a type keep Vetro's icon; and if a file cannot be loaded the tile falls back to Vetro's icon as before. About three in four of Samsung's types have such a picture (the ones without are mostly speakers, headphones and USB-C). Checked against the stock packages of Tizen 6.0, 6.5, 9 and 10 and the Q80A's input list; the WebP form has not been shown on a Tizen 9 TV yet.

### Live TV

- **The remote's Channel Guide key opens Vetro's TV guide** ([#340](https://github.com/andrearicci93/vetro/issues/340), read on a QN74F, Tizen 10). Samsung's own Guide key is code 130 on the firmware of 2021 to 2025; the tuner only knew the codes 362 and 365 of other remotes, so Samsung's guide opened instead. The tuner reads 130 as a Guide key now, like 362 and 365: it opens and closes Vetro's guide, and the Vetro UI key list warns if a shortcut of yours uses it. Not tried on a TV yet: whether Samsung's own guide still comes up behind it on this remote is for the reporter to say; until then the Remapper shortcut `130 → Up` with interception on, which the report used, keeps working.

### Remapper

- **Only when the screen is on, or off.** A shortcut, or a Home Assistant / HTTP rule, can now be limited to the moments the picture is on or off (Picture Off), with a new choice at the end of both rule forms. The TV's picture state is read once, when such a rule fires; rules without the choice read nothing and work as before. With the picture off only Power (and Volume and Mute, while Vetro's Volume bar is off) reach a shortcut: any other key brings the picture back and does nothing else, so "off" is for those keys and for Home Assistant and HTTP rules. If Vetro cannot read the picture state the rule does not run. Rules with a condition are saved apart from the others (their own part of the shortcuts file), so going back to Vetro 0.7.1 keeps every other shortcut and the conditioned ones are still there when you update again (while on 0.7.1 they are simply not run). A Settings file that has one is refused by 0.7.1 for the Remapper part only, nothing is overwritten. The diagnostic report counts the rules with a condition and says how the last one was decided (met, notMet, unreadable). Tried in unit tests and the preview only, not yet on a TV.

### Launcher

- **TV and HDMI tiles work again on 2025 Samsung TVs** ([#333](https://github.com/andrearicci93/vetro/issues/333), reported on an S95F and an S95H, Tizen 9, firmware 1301.0). The launcher switches an input with a request to Samsung's TV app that carries one of Samsung's own input icons, and it sent nothing when it found none. Samsung's 2025 firmware keeps those icons as WebP files where older TVs have PNG files, and Vetro looked only for PNG. It now accepts both, and when a TV has neither it presses the input's key, as the dashboard's Inputs page already did. The Sources page, pinned inputs and the Remapper take the same path. The diagnostic report's launcher events now say how an input was switched (`source 16: request with icon`, or `no icon, key …`), without the input's name. Found by reading the stock 2025 firmware package and the reporters' code pointer; not tried on a 2025 TV yet (the tests cover the icon choice and the key fallback). Names and pictures of the HDMI inputs (#297) are a separate matter and are not changed here.

- **The launcher no longer freezes the remote for 20 seconds after a crash, and comes back at once** ([#335](https://github.com/andrearicci93/vetro/pull/335) by [swiezaczek](https://github.com/swiezaczek), read on a 2023 S90C, Tizen 9). The volume bar's screen check started a program through .NET's `Process`, which EFL's own child handler can interfere with; on that TV the launcher aborted on the next program it started, and Samsung's crash handler then held every thread for about 20 s while the launcher kept the Home key grab, so the remote did nothing, followed by up to a minute until Vetro's supervisor started it again. The check now uses the same `popen` call as the rest of the launcher, the launcher marks itself as not dumpable so that handler does not stall it, and its systemd unit has `Restart=on-failure` (200 ms): after a crash it is back at once. Stopping it from Vetro is not a failure, so it stays down, and systemd's own limit (5 starts in 10 seconds) ends a crash loop. The probe now has no 500 ms limit (it runs in the background and only moves the bar's edge once it answers). Ported with comments; the reporter's tests on the S90C are in the pull request, the stop-versus-restart behaviour was checked on a Q80A.

- **Choose the order of the Control center cards** ([#337](https://github.com/andrearicci93/vetro/pull/337) by [swiezaczek](https://github.com/swiezaczek)). Under Vetro UI, Launcher, Control center, a Card order bar shows the enabled cards in the order the launcher uses (Left and Right move through them on the TV). Drag a card to a new place, or hold and drag on a phone, or tap one card and then another, or pick one and use the arrow keys. The new order is held as a draft (an "Order changed" mark with Apply order and Cancel), so the launcher restarts once, when you apply. Turning a card on now adds it at the end instead of putting it back in the old fixed order. The launcher and the service already kept the saved order; this only adds the way to set it. Looked at in the preview with the tap route (the drag and touch routes are covered by the pull request's tests); not tried on a TV.

- **Two switches for the Sources page: Connected sources only, and Hide TV** ([#330](https://github.com/andrearicci93/vetro/pull/330) and [#332](https://github.com/andrearicci93/vetro/pull/332) by [enij90](https://github.com/enij90), read on a 2021 AU8070, Tizen 6.0). Both are off by default and live under Vetro UI, Launcher, Customization. *Connected sources only* lists TV and the HDMI ports Samsung's source caches report as connected; a port whose device is switched off reads as unplugged, and so does one the caches do not list at all, so it is left out until Samsung's cache says otherwise (the switch says so). *Hide TV on Sources* removes TV from the Sources page for a TV with no antenna: the tuner, Remapper keys to TV and a Live TV tile on the row are not touched, and TV stays if hiding it would leave Sources empty. Both are saved in the Settings file. Tried by the author on the AU8070 and in unit tests; not on another TV (the Q80A's cache lists no HDMI port, so *Connected sources only* would hide all of them there).

### Dashboard

- **Sign-in cookie on six more calls, and two places that escape names** ([#265](https://github.com/andrearicci93/vetro/pull/265) by [swiezaczek](https://github.com/swiezaczek)). With pairing on, six of the dashboard's own requests (the diagnostic download, uninstall, plugin install, the wait for the new version after an update, Apply update, and the Remapper's listen stop when the page closes) did not send the session cookie in browsers whose default is to leave it out (before Chrome 68 and some embedded web views), so the service answered 401. They now ask for it on the same origin only; the calls to GitHub and the Shard catalog still send none. A Shard's card name in the Overview and a setting's id, range and value in the settings editor are now escaped like the rest of the page.

### Quick settings

- **Keep TV-Store running with the TV (Experimental).** Some firmware drops TV-Store's start-at-boot flag every time TV-Store is installed or updated, so its switch "Update while TV-Store is closed" does nothing. With this switch on, Vetro puts that one flag back (the same write as the Task manager's startup switch) at every start and every half hour, and turning it off puts the flag back the way the firmware had it when Vetro was the one that set it. It is off by default: where the flag is on, TV-Store's service runs from the start of the TV and its port 8077 is open in your home network, even with every switch of TV-Store off. TV-Store's Settings say when the TV last started it by itself. Idea and first version as a Shard by [PatrickSt1991](https://github.com/PatrickSt1991) ([vetro-plugins#47](https://github.com/andrearicci93/vetro-plugins/pull/47)).

## 0.7.1 — 2026-11-26

### Home Assistant (MQTT)

- **A Channel sensor.** While Vetro's tuner runs and the input is TV, Home Assistant gets the channel on screen as `21 Rai 4`, with the number, the name and whether it is a Samsung TV Plus channel as attributes. It changes with every zap and is unavailable on other inputs or with the tuner off.
- **No more program started every 10 seconds.** Volume, mute and input were read by starting a small .NET program at each read, which costs memory and processor time on 2 GB TVs. Vetro now reads the TV's own settings for them in one short command (about 34 ms on a Q80A); the program is only the fallback for a TV where those settings cannot be read.
- **Mute follows the remote's Mute key.** It was read from the audio library, which keeps saying "not muted" when the TV is muted with its own key; it now comes from the TV's own mute setting as well.
- **DisplayPort** shows as a source on Samsung monitors (#215).
- **Power and DisplayPort as keys to send**, for a Home Assistant rule or a Remapper shortcut ([#303](https://github.com/andrearicci93/vetro/pull/303) by [bmfurtado](https://github.com/bmfurtado)). Power is the remote's power key; on a monitor that toggles standby, so check the state before sending it again. DisplayPort asks the TV to switch to it the way the launcher's input tile does; it is for Samsung monitors, a TV has none.

### Inputs

- **Samsung Odyssey OLED G8 inputs** ([#314](https://github.com/andrearicci93/vetro/pull/314) by [paradox12357](https://github.com/paradox12357), tested on an LS34BG850SNXZA, firmware 1720.7, Tizen 6.5, [#316](https://github.com/andrearicci93/vetro/issues/316)). Vetro 0.7.0 offered TV and HDMI 1-4 on this monitor, left out USB-C and sent TV-only key codes for HDMI. When Samsung's source list holds exactly one HDMI, one DisplayPort and one USB-C port, the launcher's Sources, the Remapper and Home Assistant offer those three and switch with the launcher's own request to tv-viewer, then read the input back and report an error if the monitor did not change. Any other device keeps TV and HDMI 1-4 (plus DisplayPort where Samsung's list has it) and its keys as before. The camera tile some monitors list (USBCAM, type 67) is not a port.
- **Switch input from the TV manager.** Settings and controls → Sources now has one button per input, with the current one marked and a Refresh button, on TVs and monitors alike (`GET`/`POST /inputs`). A Remapper shortcut for a monitor's input is saved as `KEY_INPUT_<type>` and is part of the Settings file like any other shortcut.
- **The diagnostic report lists the input types** the launcher offers (`launcher.inputTypes`) and whether it uses the monitor layout (`launcher.monitorInputLayout`).

### Remapper

- **Turn off screen** (asked on Discord). A new action next to Open app and Send key: one remote button switches the picture off while the music plays on (Samsung's Picture Off, the same one as the last row of the Audio output card). The key that turns it off also turns it back on, as does any key except Volume and Power; that key does nothing else. It works while the remote interception is on and the remote is held by Vetro, and it can be set from Home Assistant and HTTP rules too. A TV that refuses it does not pause the interception. Tried on a Q80A: the TV's power state goes to Picture Off within 0.3 s and the same key (or any other key) wakes it; the panel itself was not watched.
- **Settings file and diagnostics.** The rule is saved in the Settings file with the other Remapper rules (an older Vetro refuses the file's Remapper part, the rest loads). The report's `input` section counts the enabled Turn off screen rules (`screenOffRules`) and says how the last one ended (`screenOff`: ok, refused or failed, and how many seconds ago).

### Task manager

- **The CPU column stays when more cards are open** ([#283](https://github.com/andrearicci93/vetro/issues/283), asked by antonio1475). A narrow Task manager card, beside the Audio output or Timer card, used to drop it; it now keeps CPU and memory and gives the app name about 190 px instead of 250.

### Settings file

- **Save settings / Load settings** (General → Settings file, [#307](https://github.com/andrearicci93/vetro/issues/307), asked by MaomaoADHD): one JSON file with your Vetro choices, to keep before a firmware update, a Smart Hub reset or a move to another TV. It holds which launcher is on and its switches (not the order of the dock's tiles), the Control center cards, Vetro TV Tuner on or off, the Remapper rules, Essential settings, HbbTV, Extra performance mode, Keep removed apps removed, the Quick settings groups you switched off, DNS blocking, MQTT and which Shards are on (not their own settings, and not single components disabled in Apps and processes). It never holds passwords, pairing, the device id or what Vetro recorded to put back later (the apps it disabled, the previous values, the uninstall list), so Restore the TV keeps working after a load. Quick settings and DNS blocking are saved only while Root access is connected.
- **Loading shows what would change first** and makes the changes only after you confirm, one at a time, through the same requests as the switches on the page, so the service checks each one as usual. The confirmation says how many Quick settings groups will be switched off; a load never switches a group back on. What needs root is listed as not loaded while Root access is away; Shards that are not installed, apps a group does not find on this TV and Samsung Home are listed too, with what to do. A file from a newer Vetro is refused. Not tried on a TV yet: tested on the dashboard preview and with the service tests.

### Tizen 10

Checked against the firmware of a 2026 Tizen 10 TV and the diagnostic reports of three TVs on it (Q70F, U8000F, QN900F). Most of Vetro already works there: Samsung Home starts (its app is still `com.samsung.tv.csfs`), the remote interception holds the remote, the Volume bar draws and takes the level, and the picture modes read as on Tizen 9. Not tried on a Tizen 10 TV with this build.

- **The network details of the diagnostic report no longer fail on Tizen 10.** On the first two Tizen 10 reports the *network* section was empty (command not found): Vetro now looks for `ip` in the system folders too, and a part that is missing leaves only its own lines empty.
- **The diagnostic report says where Samsung Home's row comes from.** Tizen 10 keeps the row in a database of its own app (`com.samsung.tv.home.mainhub`) and, from what Samsung's firmware shows, only copies the old cache file Vetro reads instead of writing it. Vetro does not read that database, and does not take a copy that Samsung moved into its folder as the row: where no cache file is found, the row is the list of installed apps, as on a 2022 TV. The report now shows `launcher.rowFrom` (where the row would come from: `csfs`, `media` or none) and which of these stores the TV has (yes/no only). It asks the TV itself, so it is there also with the launcher off, and the next Tizen 10 report settles whether the row there is Samsung's or Vetro's own list.

### Update lock

Re-checked against the firmware of 2021 (Tizen 6.0), 2022 (Tizen 6.5) and 2024 (Tizen 9) TVs after [#308](https://github.com/andrearicci93/vetro/issues/308), where a Samsung firmware update reached a TV with the update options on. What happened there is not known yet; these close the gaps the check found. Not tried on a TV yet.

- **Samsung's own update mode is kept off.** Samsung's update software, its update pop-ups and the apps that use its library can ask the TV to restart into a separate update mode, which starts before any app (Vetro included), so none of the stopped services and none of Vetro's boot steps are there, and installs from Samsung's servers, also an update downloaded and held back earlier. *Block firmware and software updates* now removes that request when it is turned on and at every restart, and while it is on, a small system unit removes it as soon as it is written. A USB update from the TV menu needs the switch off.
- **Samsung's switch for that update mode stays off.** When an update is too big for the TV's own storage (as an update to a new Tizen version can be), Samsung's update software leaves the download to the separate update mode, but only while a setting of its own allows it. That setting is off in the factory settings of 2021, 2022 and 2024 TVs; the switch now keeps it off, also at every restart, and turns it back on only if it was on when the switch was turned on. The setting is kept by the TV, so it also applies in the update mode, where nothing of Vetro runs.
- **One more update service is stopped**: the helper the app-binary updater uses to say a download is ready.
- **Two update servers one owner reported** (`otn2.samsungcloudcdn.com`, `qoe.samsungcloud.tv`: blocking them stopped the "update available" notice) go into Vetro's DNS blocking list with the switch, and are taken out again when it is turned off (only the ones Vetro added). They are blocked only while *Enable DNS blocking* is on, and only while Vetro runs, so they are also a new group on the DNS blocking page and in the lists for your router, which also covers the update mode.
- **A TV that had the switch on before 0.7.1 gets all of this by itself** at the first start of 0.7.1, without turning the switch off and on. The switch reads *Partly done* when the new guard is not running, and the diagnostic report says how many update units are stopped, whether the guard runs, whether Samsung's update request is there, whether Samsung's switch for the update mode is on and whether the update servers are blocked.

### Quick settings

Ideas from [samshush](https://github.com/elithrar/samshush), checked on a Q80A and re-written for Vetro.

- **Voice services, Bixby and Samsung Health also use Samsung's own "do not start" files.** Their background services are started by units that skip the start when such a file exists; turning the switch off now puts the file down where the TV's units look for one, and on takes it away. The switch says *Partly done* when a file is missing while the apps are off (a switch turned off before 0.7.1: turn it off again), or left while the apps are on again. Restore the TV removes every file Vetro put down. Not yet tried with a voice remote on a TV.
- **Stop viewing-data collection on Tizen 9** also masks `contents-cognition-service-manager`, `psid-checker` and `screen-analysis-service-manager`, and leaves alone a "do not start" file the TV's installer wrote for a disabled package; **Disable AirPlay** also stops Tizen 9's `airplay-app-2` ([#279](https://github.com/andrearicci93/vetro/pull/279) by swiezaczek, the parts that fit Vetro's masks).
- **Stop viewing-data collection** also stops `abnormal_user_behavior`, `issue_report_agent` (diagnostic reports) and `media-analytics-service`, and the services without a file of their own are now masked until the next restart and masked again about 10 s into every boot, through the boot step the update lock uses, instead of being stopped once Vetro's service is up (about 95 s on a Q80A). `data-service` is still only stopped.
- **New switches**: *Disable Samsung remote support* and *Disable Wi-Fi presence* (Privacy and ads), *Disable background app delivery* (General → Essential settings). Each shows only on a TV that has its services. Remote PC is left alone.
- **Samsung TV Plus** off also turns off Samsung's "start TV Plus at power-on" setting; on, or Restore the TV, puts back the value it had.
- **Stop viewing-data collection, off and on again, keeps the DNS filter on.** When the usage-log host was the filter's only domain, turning the switch off emptied the list and switched the filter off, and turning it on again added the host back but left the filter off (found on a Q80A while benchmarking 0.7.1). Vetro now switches the filter back on if it was the one that switched it off.
- **A stopped app is checked by its own process**: a switch turned off reports a member whose process is still there after the stop, by the process's label, instead of trusting the stop's answer.
- **Four more Disable switches from samshush**, each shown only on a TV that has its apps: **Gaming Hub** (the cloud gaming screen and its background service, which runs on most TVs, about 11 MB), **SmartThings** (asks first: the phone app and anything that goes through SmartThings lose the TV), **SmartThings Find** and **Sound Sensor and Pet Care**. Gaming Hub also puts down Samsung's own "do not start" file for its daemon: its unit restarts every 2 s when the app is disabled without it (1,509 restarts in under two hours on a Q80A where it had been disabled by hand).
- **A background service disabled by itself in Apps and processes gets Samsung's "do not start" file too**, where a Disable switch uses one: Gaming Hub's daemon and the voice services. Without it a disabled Gaming Hub daemon restarts every 2 seconds for as long as the TV is on (seen on a Q80A and on four other TVs in public diagnostics). Enabling it again takes the file away.
- **content-grab-service is no longer part of *All advertising and tracking*.** It passes remote control keys to a cable or satellite box connected to the TV, and Vetro described it as a picture grabber. Where an earlier Vetro switched it off, it is switched on again the next time that switch is used, or by Restore the TV. Found while reading [samshush](https://github.com/elithrar/samshush).
- **Samsung TV Plus off no longer stops channel changes on live TV** ([#299](https://github.com/andrearicci93/vetro/issues/299), reported by adamoberley on a 2024 The Frame). The switch also stopped `slive-provider-daemon`, TV Plus's channel service, and Samsung's live TV app is one of its clients. It now stops the TV Plus app, its helpers and the player, and leaves the channel service on (it frees about 15 MB instead of 25). Where an earlier Vetro stopped it, it is switched on and started again the next time the switch is used, or by Restore the TV. TV Plus channels can still be listed among the channels, but do not play.
- **Quick boot says where it helps**: measured on a 2021 Q80A (Tizen 6.0); on a 2024 The Frame (Tizen 9) it saved no time, because Vetro starts there inside Samsung's shared web service process, which comes up at the same time either way ([#300](https://github.com/andrearicci93/vetro/issues/300), measured by adamoberley).
- **A new Experimental tab** holds *Quick boot* and *Hide remote key guides*: the settings that are new or may not work on every TV, said once in the tab instead of on each card.
- **Extra performance mode** (Experimental): closes apps left in the background for 15 minutes, or the longest-idle one after 2 minutes when the TV has less than 500 MiB available. Never closed: the app on screen, apps that report playing sound (an app's own audio stream, or a player such as Spotify that tells the TV it plays), Vetro, the TV's own apps, Samsung Home and the apps you choose. It changes no other setting: Reduce motion, Close idle Samsung Home, Stop viewing-data collection, Multi View autostart and Ambient keep their own switches. The background app selection follows *Free up RAM* from [#281](https://github.com/andrearicci93/vetro/pull/281) by swiezaczek; on a 2021 Q80A background apps are told by their memory priority, as that TV has no background cgroup. The diagnostic report says whether it is on, how many apps it keeps open and how many it closed (counts only, no app names).

### Launcher

- **Close idle Samsung Home** (Vetro UI → Launcher, on by default): while Vetro's launcher is on, Samsung Home and its background parts are closed 25 s after the TV wakes from standby, or after 10 minutes unused, never while Samsung Home is on screen (on 2021 TVs Vetro asks the window manager, because the TV keeps naming the app under Samsung Home's bar). Samsung Home takes about 67 MiB on a Q80A; on 2022 and later TVs its media hub, the Home you see there, 63-118 MiB in the diagnostics ([#281](https://github.com/andrearicci93/vetro/pull/281) by [swiezaczek](https://github.com/swiezaczek)).
- **The Samsung Home closed after a boot is closed whole and never from the screen**: the media hub and sidebar go too, and never while Samsung Home is on screen; then Vetro asks again later ([#278](https://github.com/andrearicci93/vetro/pull/278) by swiezaczek).
- **Smoother launcher on busy TVs**: the checks that started a shell on the launcher's own loop now run beside it, so an opening no longer waits for them (on an S90C the longest step of an opening went from up to 1 s to under 8 ms); the launcher and the Volume bar are raised over other windows when they open ([#285](https://github.com/andrearicci93/vetro/pull/285) by swiezaczek).
- **Back no longer reaches the app under the launcher.** Back and Exit close the launcher, the Task manager and the osd 123 when the key comes up, not when it goes down: closed on the press, the launcher handed the rest of the key to the app below, and YouTube left the video it was playing (reported on an S95F in [#284](https://github.com/andrearicci93/vetro/issues/284) by tpreston1989, reproduced on a Q80A).
- **Reduce motion now covers the Volume bar and the osd 123 too**: with it on they appear and go at once, like the launcher, the Task manager and the tuner.
- **The Task manager leaves Tizen 9's volume app and quick launch alone** ([#281](https://github.com/andrearicci93/vetro/pull/281)).
- **HDMI names and pictures from Samsung's Connected Devices** ([#297](https://github.com/andrearicci93/vetro/issues/297)). Vetro read only the first of the two source lists Samsung Home keeps, which on newer TVs can be an old copy without the names you gave the inputs; it now reads both and uses the newer one. *HDMI source images* now shows the pictures Samsung keeps for the devices it recognises (consoles, boxes), which were refused before; Samsung's generic device-type icons are SVG files the launcher cannot draw, so those inputs keep Vetro's own icon.

- **One YouTube tile with Fix TizenTube on** ([#298](https://github.com/andrearicci93/vetro/pull/298) by [chemicalsno](https://github.com/chemicalsno)). On TVs whose row does not come from Samsung's Home row, Samsung's YouTube was added next to the TizenTube tile, which already wears YouTube's icon. It stays in All apps. **Fix TizenTube also covers All apps and your own row** ([#306](https://github.com/andrearicci93/vetro/pull/306) by [adri0894-web](https://github.com/adri0894-web)): TizenTube added from there gets YouTube's icon and closes Samsung's YouTube first, as in Samsung's row.
- **The Volume bar on the left or right edge of a Samsung ultrawide monitor** (Odyssey OLED G9) sits at the panel's edge, not at the edge of a 16:9 area in the middle ([#305](https://github.com/andrearicci93/vetro/pull/305) by [bmfurtado](https://github.com/bmfurtado)). The screen check runs beside the launcher, so no TV waits for it.

### Live TV

- **The tuner starts on a UE55AU7105 (2021, Tizen 6.0)**, where it stopped with a stack overflow before reading the channels ([#306](https://github.com/andrearicci93/vetro/pull/306) by [adri0894-web](https://github.com/adri0894-web)). Samsung's TV client is also looked for in Game Bar's folder, after the firmware's own folders.
- **The tuner reads its remote more safely** ([#268](https://github.com/andrearicci93/vetro/pull/268) by [swiezaczek](https://github.com/swiezaczek)): a half-read key record is carried to the next read, a remote that disconnects (end of the node's stream) is dropped, the held-key repeat stops when the Dock or a launcher window takes the keys, when the Channel list or EPG closes, or when the tuner is not on screen, and a signal arriving in the middle of a read no longer loses it.
- **The osd 123 sends its digits to Samsung's app until the tuner has a Channel list** ([#286](https://github.com/andrearicci93/vetro/pull/286) by [swiezaczek](https://github.com/swiezaczek)): with no list, a `tune N` did nothing. The tuner also asks for the list again as soon as the TV goes back to its own tuner, not after the back-off.

### Updates

- **Updates from the dashboard start on 2022 and later TVs** ([#296](https://github.com/andrearicci93/vetro/issues/296), cause found by adamoberley). On Tizen 6.5 to 9 Vetro's service runs inside Samsung's shared `wrt-service` process, and restarting the service there keeps the old code loaded: the new version never ran, and after 4 minutes the old files were put back (*The last update did not start*). From 0.7.1 an update ends that process and starts the service again, so the new files load; any other web service running in that process is ended with it. TVs where the service has a process of its own (Tizen 6.0 and older) restart as before.
- **Coming from 0.7.0 on a Tizen 6.5 or later TV**, 0.7.0's updater still does the restart, so the problem above still applies to that one step. Once the dashboard says *Updating…*, restart the whole TV within 3 minutes (hold the remote's power button until it restarts, or unplug it for 30 seconds) and the new version starts. Or install it with Apps2Samsung.
- **The Software update box says what to do if an update does not come back**: if the new version is not there 2 minutes after *Updating…*, restart the whole TV (hold the power button, or unplug it for 30 seconds; standby is not enough). It is a fallback for the restart above, which no Tizen 6.5 or later TV has run yet; the previous files are still put back after 4 minutes if the new version never starts.
- **A failed earlier update no longer shows as the result of the next one.** The dashboard said *The last update did not start* during a new try, from the record of the try before.
- **From 0.5.0, install 0.7.1 with Apps2Samsung.** The 0.5.0 updater writes the whole update as one script, which the root agent takes up to 64 KiB only, and 0.7.1 changes more files than that holds. A TV on 0.5.0 now refuses the update as soon as it checks it (*Path not allowed in an update: payload/net6/…*), before anything changes, instead of failing half way through. TVs on 0.7.0 update from Quick settings as before.
- **An update can replace every file of Vetro at once.** The update script lists the files once and loops over them, about 150 bytes per file instead of about 1 KB, so from 0.7.1 on a whole package fits. Go back and the watchdog keep the same files on the TV, and Go back from 0.7.1 also undoes the update that 0.7.0 applied. Tried with bash and dash against a test folder; not yet on a TV.
- **Go back works after an update of the launcher or the tuner.** In 0.7.0 it put the previous files back and then stopped with an error before restarting Vetro: the launcher and tuner run as temporary system units, and the step that clears a stopped unit's failure state fails once such a unit is gone. Go back now carries on whatever that step says (found on a Q80A while testing 0.7.1).
- **The .NET 6 root helpers are in updates again** (`payload/net6`, #226). They have not changed since 0.5.0, so a TV on 0.7.0 already has the same files and nothing is copied.
- **Go back no longer races the watchdog of the update, and a damaged backup record is refused** ([#264](https://github.com/andrearicci93/vetro/pull/264) by [swiezaczek](https://github.com/swiezaczek)): a Go back pressed while the update waited for its confirmation put the files back twice and restarted Vetro three times; it now leaves a mark the watchdog sees. A backup record whose versions are not plain numbers (the version goes into a line the root agent runs) is not offered and not used.
- **Erase all data also removes the launcher's Home markers** ([#287](https://github.com/andrearicci93/vetro/pull/287) by [swiezaczek](https://github.com/swiezaczek)).

### Shards

- **A Shard file can be chosen on an iPhone or iPad.** Safari greyed out `.vplugin` files in the file picker, because the page asked for that extension and iOS knows no file type for it. The picker now shows every file and Vetro checks the name after the choice.
- **YouTube opens through its Shard from every door** ([#323](https://github.com/andrearicci93/vetro/pull/323) and [#324](https://github.com/andrearicci93/vetro/pull/324) by [swiezaczek](https://github.com/swiezaczek), tested on a QE65S90C, Tizen 9, fixes [#207](https://github.com/andrearicci93/vetro/issues/207)). On TVs that also have Samsung's YouTube wrapper (`9Ur5IzDKqV.TizenYouTube`), the launcher's row, All apps and a Remapper, MQTT or HTTP rule now start the Shard instead of the unpatched app; a Shard that cannot start it leaves the app starting by itself. A Remapper rule does not wait for a slow Shard (the other actions are not held up). When the root agent is not connected, a Shard tile starts the app at once instead of doing nothing.
- **Plugin switch off and on, then SIGTERM.** A plugin whose `stop()` is asynchronous is waited for before it is started again (and before the service exits, up to 4 seconds), two quick launches of one app start it once, and a plugin that exports `onAgent(connected)` hears when the root agent comes and goes.
- **The launcher restarts after a same-version reinstall.** The launcher DLL is now remembered by a short hash, so a `.wgt` reinstalled with the same version number no longer leaves the old DLL running. A refresh of the launcher lists that fails is tried again (5 times at most), and the launcher is not raised over an active screensaver at power-on.
- **Diagnostics: the screensaver check** no longer matches its own shell, and also knows the Tizen 9 screensaver processes (`spotlight-ss`, `scm-screensaver`).

### Quick settings

- **Allow SDB from the local network is now in General → Essential settings**, no longer under Developer settings: turning it on improves compatibility with Apps2Samsung and TV-Store.

The new **Uninstall** tab deletes the same apps (not YouTube: switch it off instead), Samsung TV Plus (its background services stay: Disable stops them) and the e-Manual (21 to 124 MB). - **Vision AI** (2024 and later TVs that have it). Holding Home, or the AI button of the newer remotes, opens Samsung's AI screens (Click to Search, the AI companion); turning off Bixby does not stop it. The new switch on the Disable tab turns those apps off, so nothing opens. A short Home press works as before, and the Vision AI row of Samsung's Home stays.
- **The firmware switch now blocks every update path, not just the menu setting** ([#223](https://github.com/andrearicci93/vetro/issues/223)). "Auto update" only changes what the SWU daemons do with a downloaded image: the background loop, the app/package updater, the app-binary (EMP) manager, the VD system updater and the preview updater never read it. The switch (now **Block firmware and software updates**) stops and masks all of them, turns the auto-update and EMP switches off, removes the download markers and re-applies the lock after every restart; the installers are stopped too, since the TV keeps two complete boot slots and an interrupted write cannot damage the running one. Where the TV runs the AT-HUB boot step (Tizen 6, 6.5 and 9), the lock is also applied at power-on, before the update services start, by a small replacement of its `parseinfo.sh` that keeps the vendor write, is removed when this switch and Quick boot are both off, and does nothing once Vetro is uninstalled; on other firmware it starts with Vetro's root agent. USB recovery is left working. Read from the Tizen 6, 6.5 and 9 firmware; tried on a Q80A (fw 2310.0) after a cold reboot on 2026-11-20, where the early masks were in place 15 s after boot, before Vetro's service. Other models are not tried.
- **Quick boot (Experimental)**. The TV waits for four boot-completion markers; two never appear because Samsung's units run as an unprivileged user, so Vetro used to start about 30 s late. The new switch in **Essential settings** creates the four markers at ~10 s through the AT-HUB step, without touching the update services: on a Q80A Vetro went from ~97 s to 28-31 s and the launcher from ~103 s to 42-45 s. It uses the same vendor-script replacement as the update lock; turning it off while the update lock is off too (or Restore the TV) brings the vendor boot step back. On Tizen 6.5 and 9 it also sets the system-default event the user boot waits for (those models are untested). Experimental: tested on a Q80A only; another model or boot order may differ. The section that held **Block firmware and software updates** is now **Essential settings**.
- **Hide remote key guides** (Essential settings). 2024 and later TVs show a picture of the remote ("Press Volume: Mute", play / pause) again after every power-on; the switch marks those guides as seen now and after each boot. Read from the Tizen 9 firmware; not yet tried on such a TV.

- **Keep removed apps removed** is now on the Uninstall tab.
- **Uninstalling no longer leaves a dead tile.** Vetro now also removes the Home line, the registry row and the icon that `pkgcmd` leaves behind (while Samsung's Home is running, it may finish its own row later), and **Rebuild app list** clears old ones.

### Fixes

- **App icons that are not square fill their tile.** A wide or tall icon was shown whole with blurred bands above and below it, which some TVs drew as coloured noise; it now fills the tile, cut to its middle.
- **The diagnostic report keeps every part of the launcher, tuner and remote logs in place.** When two parts in a row were empty, the later ones moved up one, so the remote helper's result came back empty. The tuner's part now also says which input the TV reports and what Live TV did with a Samsung TV Plus channel.
- **Live TV leaves Samsung TV Plus.** Samsung's live TV app goes back to its last channel, so after a Samsung TV Plus channel the Live TV tile and TV in Sources brought TV Plus back, with Samsung's own screens instead of Vetro's tuner. The launcher now tells the tuner that you chose the TV input; when the channel on air is a TV Plus one, the tuner switches to the last antenna channel you watched with it (or the first one) and comes up. The Samsung TV Plus tile still opens TV Plus. Tried on a Q80A.
- **Holding Up or Down in the Channel list runs down the list again** ([#268](https://github.com/andrearicci93/vetro/pull/268), by [swiezaczek](https://github.com/swiezaczek)). On remotes that send a release for every key, the 0.7.0 previews moved one row only, because the guard against double steps also stopped the hold's own steps. Holding CH and moving in the TV guide were not affected. Tried on a Q80A.
- **Restarting the launcher or the tuner no longer waits on systemd** ([#258](https://github.com/andrearicci93/vetro/pull/258), by [swiezaczek](https://github.com/swiezaczek)). Vetro asks systemd to stop the unit without waiting for its answer, then checks that the unit is gone (up to 3 seconds) and clears a failed state before starting it again. Tried on a Q80A: Volume bar edge changes, launcher and tuner off and on, standby and wake.
- **Video no longer plays in Samsung Home's picture mode with the launcher on.** Samsung's Home puts the TV in its own picture mode while it is on screen and gives the picture back when an app opens; with Vetro's launcher Samsung's Home is not running, so the TV stayed in that mode (motion smoothing off) under every app, and video looked sluggish (found in an S95C's diagnostics, launcher on vs off). Vetro now gives the picture back the same way when another app is on screen: right after the launcher closes and at each check of the launcher. Not yet tried on a TV.
- **The Audio output card keeps the optical row** after you switch to the TV speakers from Samsung's menu: Vetro now notes the external output on every Vol press too, not only when the card opens.
- **An optical soundbar follows Vol again with Vetro's volume bar on.** Vetro changed the TV's own level, which a soundbar on optical (driven by the TV's infrared remote or Q-Symphony) does not follow; on optical, TV + optical and the centre modes Vol and Mute now go to Samsung, as with a receiver on HDMI, and Samsung's bar shows. Seen on an S95C, an S90D with a HW-B650 and an S90F with Q-Symphony, each working with the bar off; the change itself is not yet tried on a TV.
- **Moving an app in the launcher's row shows on screen.** While a tile was moved, the row kept drawing the icons where they were, so the order on screen did not change although the new order was saved (seen on a Samsung The Frame LS03B). Checked in the preview; not yet tried on a TV.
- **Bluetooth headphones follow Vol with Vetro's volume bar on.** Vetro changed the TV's own level, which Bluetooth headphones do not follow (seen on a Samsung The Frame LS03B); on Bluetooth, Vol and Mute now go to Samsung too, and Samsung's bar shows. Not yet tried on a TV.
- **On-screen displays says what the volume bar does with your sound output**: one sentence for a receiver on HDMI, the optical outputs and the others.
- **One slow command no longer cuts Vetro off from the TV.** When a command answered later than its time limit, Vetro closed its connection to the root helper; every command after it failed until the helper was started again, which takes seconds. Two diagnostic reports lost most of their sections to a dropped connection; a late answer is one way that happens. Now the caller is told the command ran out of time, the next command waits for the late answer, and the connection is closed only if the helper stays silent half a minute longer. Diagnostics say why the helper was lost each time and how many answers came late.
- **Diagnostics name why a section is missing when the root connection drops** (a command that timed out, a busy queue) instead of a bare "error", and carry the sound output's universal-remote state (whether Samsung's universal remote runs, its activities as numbers, the infrared volume flag).
- **Vol and the 123 key reach Vetro's volume bar and number pad where the TV does not let the service write to the launcher.** Vetro's service handed these two keys to the launcher itself, and on the 2022 and later TVs whose diagnostics we have, no Vol or 123 press ever arrived (an S95B's report showed the keys held and nothing drawn). When the service's own write fails (refused, or the pipe not found), Vetro's root helper passes the key on; the report says which way the last one went. On Tizen 9 the refusal comes from the TV's access labels: the launcher now labels its pipe so the service may write to it ([#274](https://github.com/andrearicci93/vetro/pull/274) by [swiezaczek](https://github.com/swiezaczek), tried by them on an S90C). The fallback through the root helper is not yet tried on one of those TVs.

### Sign-in, plugins and updates

- **Pairing for the dashboard and API** ([#5](https://github.com/andrearicci93/vetro/issues/5) requested by **PythEch**; [#9](https://github.com/andrearicci93/vetro/pull/9) by **zerodevb**). Browsers and scripts pair once with a six-digit code shown on the TV. Up to 20 devices can be paired. The TV app keeps working without pairing. Pairing is **automatic**: it switches on by itself the first time the Vetro app on the TV is seen, which proves the TV can show the code. [Sign-in guide](app/docs/SIGN-IN.md).
- **Pairing is automatic, and you can choose.** Quick settings → Developer settings → Pairing has a **Require pairing** switch. By default it is automatic: until the Vetro app on the TV has been seen, the dashboard is open like Vetro 0.3.5 and says so; after that, pairing is required. Choosing On or Off replaces the automatic mode. Turning it off asks for confirmation. Restore the TV does not change it.
- **Updating from an older Vetro** (reported on Discord by **adilrazeen**, QN70F, Tizen 9). Installing 0.5.0 over 0.3.x could leave the old service running and still showing 0.3.5. When the service finds its port held by an older Vetro it ends that one and starts normally. Anything else on the port (TizenTube and tizen-youtube also use 8099) is never touched: Vetro says so in the service log and tries again every 15 seconds instead of stopping. If the TV page shows two different versions, restart the TV (unplug it for 30 seconds).
- **Vetro Shards (plugins), experimental.** Install, update and remove `.vplugin` bundles from a public catalog or a file. New plugins start switched off, and a plugin that keeps failing is stopped. If Vetro was stopped right after starting, plugins start in safe mode and the page says why; nothing is removed. Plugin pages open as tabs. Plugin code has the same access as Vetro, including root commands: permission labels are not a security sandbox. [Guide and developer tools](app/docs/plugins.md).
- **Signed plugin catalog.** Catalog plugins are checked against a signature, and invalid ones are refused. Unsigned plugins need **Developer mode**, which is off by default. Each plugin shows where it came from. A signature shows who published a plugin, not that it is safe. Plugins with accented characters now install on older TVs.
- **The launcher is the first bundled plugin.** It updates with Vetro and cannot be removed or replaced from the catalog. [Architecture](app/docs/PLUGIN-ARCHITECTURE.md).
- **Signed in-place updates, launcher included.** Software update checks GitHub when you ask, verifies the bundle, replaces the files and restarts the launcher if needed. If the new version does not start, Vetro goes back to the previous one within four minutes; you can also roll back by hand. A second update is refused while the first one waits for confirmation ([#116](https://github.com/andrearicci93/vetro/issues/116), reported by **adri0894-web**). Changes to `config.xml` still need a reinstall. Tested on a Q80A with the release key: update, refusal of a tampered bundle, rollback by hand and automatic rollback. [Update guide](app/docs/UPDATING.md).

- **Remote interception finds the remote again after Linux renumbers its inputs** ([#32](https://github.com/andrearicci93/vetro/pull/32), by tomcraft): a saved `/dev/input/eventN` is not a stable identity, and a remote that shows several interfaces under one name stayed disconnected after a restart or a reconnection. Replayed on five cases and checked by the author on a TV for the automatic reconnection; a real renumbering was not provoked.
- **The service can run on Node 4.4 (Tizen 4 and 5.5), app-only** ([#33](https://github.com/andrearicci93/vetro/pull/33), by SalustLab; issues #2 and #19): those TVs run the web service on Node.js 4.4.3, not Node 12, and the service stopped twice, while loading (`async` functions, `fs.promises`) and on the first request (`Promise.prototype.finally`, `Buffer.alloc`, `Buffer.from` with a string). Tested by the author on a QN55Q80TAGXZD (2020, Tizen 5.5): the dashboard, the app list, the diagnostics and the start after a cold boot work, 45 requests ran without a crash. - **Advertising list: two more components** ([#44](https://github.com/andrearicci93/vetro/pull/44)): `com.samsung.tv.iacr` and `com.samsung.tv.screen-analysis-dbmgr` are now listed as advertising in the Debloater and as tracking in the app catalog, instead of "other".
