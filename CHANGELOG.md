# Changelog

## 0.4.0 — unreleased

- **Diagnostic export: component details (opt-in).** The Diagnostics panel has a new switch, *Include details about unrecognised components*. On, the report adds what the package manifests of the components Vetro has no description for declare: description, privileges, whether they ask to start at boot and whether the TV registered that (`differs`), and SHA-256 checksums of the manifest and of the programs that start at boot. It makes reports from other TVs comparable (the same checksum on two TVs is the same program) and would have shown the #25 and #26 startup problem at a glance. Off by default; a few hundred small files read in small steps at the lowest priority, stopping after about a minute (not yet timed on a TV). No paths, addresses, URLs or author names. The community report check (`parse_log.py`) now knows the `launcher`, `quickWins` and `components` sections and lists components whose start flags differ from their manifest.
- **Diagnostic export: firmware and Tizen version read by the service.** Two of the last four community reports (#17, #25) had no model and no firmware, because those values come from a probe the Vetro page has to post. The service now reads the firmware (`/etc/prd_info.ini`) and the Tizen version (`/etc/tizen-release`) itself and says where each came from (`firmwareSource`, `tizenVersion`). The commercial model still needs the probe.
- **Version in the sidebar:** the footer under the app count and the connection state now says which Vetro build is running (*Vetro 0.4.0*), read from the service's `/status`.
- **Stop Ambient now holds.** On the Q80A, `screend` (Samsung's screen daemon) started `org.tizen.ambientapp` again within 2–7 s of any stop, so 0.3.0 could only offer a partial block. `ambient_app_enable=0` and `app_disable=true` in the package registry do not change that. What does: stop `screend`, kill the app, start `screend` again. `screend` does not launch the app by itself when it starts (only Samsung's `ambient_start.sh` does, at boot), so it stays off: it was still off after several minutes, and a launch made the way `ambient_start.sh` makes it was caught and ended within seconds. After each restart Vetro waits for that script to launch the app and ends it the same way. Checked on a Q80A with a real restart on 2026-10-25: Ambient was not running 337 s after the TV came back, with `screend` active and the picture normal. The win is now called **Stop Ambient** (no longer "partial block"). Opening Ambient yourself still works, and `screend` starts it again after you close it until the next stop.
- **Stop viewing-data collection (new quick win):** stops `contents-recognition-service` (recognises the app, content type and channel on screen), `canalysis`, `pisa-service` and `adagent-service` (analytics and ads), `mirroring-recognition-manager`, `contents-ui-detector-service` and `contents-ott-detector-service` (find thumbnails and app screens in the picture; the second is started by the recogniser, not by a unit), `kpi-logging` (key presses), `emergency-log-transmitter` and `devicetracker`, now and again after every restart. `canalysis` and `pisa-service` are held off across restarts by the files their own start-up units check (`/opt/usr/share/systemd/system/canalysis-daemon` and `pisa-service`; the second also covers `adagent-service`); the others are stopped at each boot, twice, 45 s apart, because some start late. `data-service`, which collects KPI logs (its configuration lists remote keys, apps, channels, volume and the advertising ID as sources; its log endpoints are on `lcprd1.samsungcloudsolution.net`, which is the address the TV was connected to; what it sends is encrypted and was not inspected), is started again over D-Bus by other components; the win adds that host to the saved list of the domain filter, and says *Uploads can resume* until **Block ad and tracking domains** is on. If the filter is off, it is not switched on for you. Switching off starts the services again and removes the host if Vetro added it. Tried on a Q80A on 2026-10-25: a restart brought back every service that has no brake file, which is why the boot step exists. With the boot step installed, a second restart left all eight stopped from the first reading (112 s after boot) to the last (376 s); only `data-service` ran, as expected, and the second pass at about 170 s changed nothing visible. Some features that report back to Samsung, such as targeted suggestions, may stop updating. `canalysis` also works on logo recognition for HDMI inputs and `pisa-service` starts feature services and handles ad terms, so source recognition or some consent screens may change; neither was tested.

## 0.3.0 — 2026-10-25

- **Port clash** (issue #16): the port is no longer fixed at 8099. `VETRO_PORT=9000 node build.cjs` (in `app/` or `rooting/`) writes the port into the widget's access origin, the probe page and the service, so Vetro can sit beside an app that already uses 8099 (tizen-youtube). The default and the default package are unchanged; a port outside 1024–65535, or 8001/8002 (used by the TV's remote sockets), is refused. It is a build-time choice, not a setting on the TV. Not tried on a TV.
- **Installation guide** (issues #11 and #12): a short version at the top (the two packages, what you do and what you do not do), the TV's *Host PC IP → 127.0.0.1* step as its own step 5, and a table for "root agent not connected" that starts from what `/status` shows.
- **Quick settings, privacy curated:** the separate *Privacy* section is gone. Its *ACR viewing data* switch only covered components that **Disable all advertising and tracking** already switches off, so it was a duplicate; the domain filter now sits under *Advertising and tracking*.
- **Launcher, Fix TizenTube:** the switch is greyed out, with the chip *TizenTube is not installed on this TV*, once the app list has been read and TizenTube is not in it (an already-on switch can still be turned off).
- **Diagnostic export:** two new sections, `launcher` (on, running, Samsung’s Home running, Fix TizenTube, Autorun Smart Hub switched off, counts, whether a TizenTube tile exists; never the log, error text or app names) and `quickWins` (auto update, MultiScreen, Ambient). 16 sections in all.
- **Staging folders:** each service start left a new `archive-root-<id>` folder and signed archive in the TV's staging folder (150+ after a few weeks, about 10 MB on a nearly full `/opt`). The service now keeps the current one and the two newest, skips a folder that appears on a running process’s command line (checked in tests only, not yet seen on the TV), and removes the rest and the archives without a folder. Reaches the TV with the next signed build.
- **Launcher (new tab):** a glass launcher for the Home key (`dock/`, a .NET process run by the TV's own `dotnet`). Turning it on, after an in-page warning, builds its app list from Samsung's own Home row (row order, registry titles and registry icons, read from the TV each time it starts), starts it, and closes Samsung's Home; Settings and Source in the launcher still open Samsung's screens. Nothing is disabled or removed: if the launcher stops, the Home key goes back to Samsung's Home, and Vetro starts the launcher again after a restart or a crash (backing off up to five minutes between tries and never switching itself off, starting it the moment the root helper connects, from the list saved by the last start). Turning the launcher on also switches off Samsung's *Autorun Smart Hub* setting (`db/menu/smart_hub/ontvsetting/auto_start`), so the TV no longer powers on to Samsung's Home; Vetro remembers the old value and puts it back only if it changed it, when the launcher is turned off. Tested on a Q80A only; experimental on other models. While it is on, the tab shows a preview of how the launcher looks on the TV. **Fix TizenTube** (a switch in the same tab) gives the TizenTube tile the YouTube icon and closes Samsung's YouTube (`com.samsung.tv.cobalt-yt`) just before TizenTube starts.
- **Dashboard redesign:** the dashboard now follows the Vetro design system (`app/design-system`: tokens, a reference page and `DESIGN.md`), shows the Vetro icon (served at `/icon.png`) and has a new first group in the navigation: **Quick settings**, **Launcher** (marked Beta) and **Remapper** (the former Remote panel). The Debloater is now **Task manager**. A test keeps the page's tokens identical to `tokens.css`.
- **Quick settings are quick wins:** every switch is worded as the win it gives and *on* means it is applied, with a chip saying *Done* or *Partly done* and a short "What this changes" note. New: **Disable HbbTV** (see below), **Disable MultiScreen autostart** and **Disable automatic firmware update** (`db/menu/support/softwareupdate/autoupdate` 1 → 0 with read-back and rollback; the value that was there is kept and restored on switch-off). Memory figures (HbbTV about 22 MB, Multi View about 15 MB) come from a process survey of a Q80A; the effect of each change on a running TV is not yet verified.
- **HbbTV:** the menu value Off does not stop HbbTV on the Q80A: the app keeps running, and `hbbtv_service` (which listens for app status changes) starts it again at boot, on a source change and when the TV wakes. Tried on the Q80A on 2026-10-23: stopping the app, even with `-k` and with the firmware's own brake file `/tmp/hbbtv_do-not-relaunch` in place, brought it back within 2–4 s; stopping `hbbtv_service` first and then the app kept it off for the 40 s that were watched, and the service did not restart by itself. Off now means the menu value 19, the brake file, the service stopped and the app stopped, in that order, and Vetro does it again after every restart of the TV. Off never starts anything; On removes the two flag files and starts the service and the app. A menu value of Off with the app or its service still running is shown as *Partly done*. Not yet checked: standby and wake, a cold boot, and the red-button deeplink from the TV viewer, which may start the app by another route.
- **MultiScreen:** the TV starts it at boot with a Samsung unit that skips itself when `.../com.samsung.tv.multiscreen/data/disable_preloading` exists; the win creates that file (owned by the app's group) and stops the app, and Multi View still starts on demand. Verified on the Q80A on 2026-10-23: systemd reports the start condition as not met and does not loop. The choices are saved in `vetro-quick-wins.json` in the share folder.
- **Ambient (partial block):** stopping AmbientApp with `-t` or `-k` does not last on the Q80A: it is back within 2–6 s. The process that does it is `screend`, Samsung's screen daemon (the app's launch record names its PID as the caller). `screend` keeps a list of apps to start again when they end, and puts `org.tizen.ambientapp` on it only when the model has the read-only firmware feature `com.samsung/featureconf/ambient_screen_support`; the only built-in brake is a flag it sets while the TV powers off. Neither of its two Ambient settings (`ambient_app_enable`, `ambient_setting`) changes this. So there is no complete block: **Stop Ambient (partial block)** stops the app now and after each restart of the TV (about 59 MB), and says in the dashboard that Samsung may start it again. The disable flag stays unused, because `ambient_start.sh` would retry forever at the next boot. Found by reading the Q80A `screend` binary; the effect on a running TV has only been timed with the stop commands.
- **Quick settings, two all-in switches:** **Disable all advertising and tracking** and **Disable all voice assistants**, each in its own section. Their members are whatever the Task manager files under Advertising and tracking or Voice assistants on the TV, except components with the role *Keep* (Smart Hub's ad agent, which Home loads) and Vetro itself; the list is shown under the switch. They use the same disable flag and rollback as the other groups and stop members that are running. The voice switch asks for confirmation: it also turns off the remote's microphone button, Voice Guide (read-aloud) and voice suggestions in search. The existing per-feature switches (viewing data, Alexa, Bixby, …) stay and show the same state.
- **Domain filter candidates:** `osb.samsungqbe.com`, `rm.samsungqbe.com` and `scs.samsungqbe.com` (found in the firmware, usage unknown) and, labelled *unverified*, `gpm.samsungqbe.com` (a guess at where the viewing-data service learns its servers). `svdca.samsungqbe.com`, which Certificate Manager needs, is on the never-block list.
- **Launcher look:** a new look, chosen in the designer page (`dock/designer`): a solid bar, smaller icons, a thin light line inside every icon, a white focus ring and a glow in the colour of the selected app (ring, glow and icons share one corner radius), the selected icon rising a little, two outline pills (Settings, Samsung Home), a “Source” hint, no name labels or clock, a cascade entrance and constant-speed focus movement. The preview in the Launcher tab follows it.
- **Diagnostics read from seven community reports:** two things had never worked outside the Q80A. The SoC temperature was empty in every report, because Samsung's TVs have no Linux thermal zones; Vetro now reads the driver's own file (`/sys/devices/platform/soc/*thermal/temperature`, whole degrees), which also fills the MQTT temperature sensor. And the CPU rate was empty in four of seven, because its second sample waited behind the slow startup listing in the TV's one-at-a-time command queue; the other reads now start after it.
- **Startup listing no longer times out on slower TVs:** it was one command that needed 13–17 s of `systemctl list-unit-files` work on a Q80A, against a 15 s limit, and the Diagnostics `startup` section came back *unavailable: command timed out* in the QN55Q65, Q65S95C and QN55S95B reports. The running states and the boot states are now two commands (the second with a 60 s limit); if the second fails, the listing still shows what runs, with the boot state unknown. The report gives this section a longer deadline.
- **Compatibility:** community report from a Samsung QN55Q65DAGXZS (2024, firmware T-NKLDUABC-0090-2123.9) on Vetro 0.2.3 (issue #10): built unsigned and loaded with apps2samsung, reported working; the export shows an authenticated UID-0 agent, the service running on Node v18.18.2 and 29 confirmed controls. Cold-boot persistence was not reported.
- **Compatibility:** community report from a Samsung Q65S95C (2023, firmware T-PTMCDEUC-0090-2220.4) on Vetro 0.2.3 (issue #13): service running on Node v18.18.2 with an authenticated UID-0 agent, 23 voice-assistant and ACR components disabled from Quick settings, button remaps in use, and 29 of 29 controls confirmed.
- **Compatibility:** community report from a Samsung QN55S95BAFXZA (2022, Tizen 6.5, firmware T-PTMAKUC-1720.7) on Vetro 0.2.3 (issue #14): root on the first try, the TV rooted itself after the Host PC IP step, and 15 of 17 ad and analytics packages were disabled and verified. Only 267 of its 368 packages are in the Q80A-based catalog.
- **Installation guide** (issues #11 and #12): a short version at the top (the two packages, what you do and what you do not do), the TV's *Host PC IP → 127.0.0.1* step as its own step 5, and a table for "root agent not connected" that starts from what `/status` shows.
- **TV page:** opening Vetro now also tries to start the background service (`tizen.application.launch('vetrotvapp.svc')`) and retries the service check for about 12 seconds, because a public-level certificate may not get the on-boot start honored (issue #2). No extra privilege is declared. Tested by a contributor on a Q60A (Tizen 6, personal certificate), where the service started on every launch. On the Q80A the call is accepted, but the system restarts the stopped service by itself within a second, so starting from a stopped service could not be reproduced there. The page also says when the service did not answer.
- **TV page:** the small Vetro page on the TV closes itself 5 seconds after the report reaches the service (or when it is hidden after that), instead of staying resident. On the Q80A its web app and web process held about 100 MiB of resident memory (RSS, which includes shared pages) in a benchmark sample; the service keeps running. A failed report leaves the page open so the error can be read. The Debloater keeps Ambient Mode (`org.tizen.ambientapp`) off the disable list, with a test, because the firmware's boot script relaunches it in a retry loop.
- **TV picture controls:** blur reduction, judder reduction, LED Clear Motion and HDMI black level can now be changed from Settings. They are firmware-derived: the D-Bus signatures come from the Q80A `avocd` handlers, and for HDMI black level (0–2) and LED Clear Motion (0–2) the decompiled menu provider passes the menu value straight to the call; for blur reduction the call is visible but not its arguments, and judder reduction was not decompiled. None has been written on a TV by the maintainer. Each is editable only after the TV's own `busctl introspect` lists the exact method and signature; otherwise the row stays read-only with the reason, and a failed check never touches the six controls verified earlier. Writes keep the read-back and rollback of the existing controls. The method list is fetched once per service run. The diagnostic export now records, for every control, whether the TV exposes it (`confirmed`, `missing`, `signature-mismatch`) and how many methods it offers, so a report from another model shows which controls it supports.
- **Diagnostic export:** sections that fail now carry a fixed-list `reason` and, for failed commands, the numeric exit code, so a missing section such as `startup` can be diagnosed from the file. Startup listing now tells a command timeout from a command failure.
- **Diagnostic export:** model, firmware and API probe are labelled as widget-reported with their age; settings write paths are reported as `implemented` instead of `verified`; the monitor takes two samples so CPU rates are filled in; the temperature is searched across all thermal zones; kernel threads are counted instead of listed; the dead `runtimeAvailability` field and idle Wi-Fi services are no longer exported; `anynet+(hdmicec)`-style menu ids are kept; `sourceDirty` records whether the package matched its revision.
- `POST /probe` is accepted only from the TV itself.
- **Domain filter candidates** now come from hostnames found in the Q80A firmware (advertising, analytics and KPI, diagnostic logs), shown in groups with their evidence; the earlier public-report names stay in a separate group. The filter refuses the names the TV uses for its internet check and clock, and `/blocklist` no longer lists the `samsungcloudsolution.com` parent domain, which external blockers would apply to those names. See [domain filter candidates](app/docs/DOMAIN-FILTER.md). Other write routes are unchanged.
- **Community report analysis:** structured reports no longer match text error signatures, and the review names the sections that were not collected and why.
- **Compatibility:** community report from a Samsung Q70A (QE55Q70AATXXC, firmware T-NKM2DEUC-2301.1) on Vetro 0.2.3: setup with root access completed, Quick settings, the Debloater and domain blocking used, and the diagnostic export confirmed 29 controls against the TV's own method list. The reporter also turned the red standby LED off and on again through the firmware's `micom_set_standby_led_state` (libmicom), outside Vetro; this is not a Vetro feature yet, and the library has no matching getter, so a switch could not read the state back. Turning off the Enlightenment effects module did not remove the Home and Settings animations.
- **Compatibility:** community report from a Samsung QN85A (GQ65QN85AATXZG, firmware T-NKM2DEUC-2301.1) on Vetro 0.2.3: app, service and UID-0 agent working and recovered after a reboot, once the reporter had enabled the service's on-boot and auto-restart flags. Installation guide: a DNS filter blocking `svdca.samsungqbe.com` makes Certificate Manager fail.
- **Compatibility:** first community diagnostic report from a second model, a Samsung Q67B (QE43Q67BAUXXH, firmware T-NKLBDEUC-1720.7), on Vetro 0.2.3. The app and service were running, the authenticated root agent was connected with UID 0, and 32 components were disabled through the registry. Not confirmed: cold-boot persistence and the system service listing, which was unavailable in that report.
- **Quick settings** is the first panel: switches for HbbTV, domain blocking, Alexa, Google Assistant, Bixby and voice services, with in-page confirmation for voice switches (the remote microphone button stops working). Groups apply the disabled flag to every installed member in one step, verify it in the registry, roll back on failure and stop members still running.
- **Install leftovers** cleanup ported from Apps2Samsung (MIT): package files in the install staging folder, deleted one at a time, with bytes freed and storage before and after. Refused while an installation is running.
- **App catalog** from the firmware manifests: area, role and purpose for each package; references from other packages, event and key-sequence launches and microphone/camera/location access in the component drawer. `app/scripts/build-app-catalog.py` regenerates `service/app-facts.js` from a private dump.
- **Debloater** layout: role filters with counts, one State column, Startup listing only flags that are on, CPU/RAM only while sampled, duplicate names disambiguated, startup flags as switches.
- The Remote panel polls only while listening; stopping capture returns to the saved interception choice.
- Navigation grouped by task; HbbTV, domain blocking and MQTT use switches; privacy values use words instead of Yes/No.
- Dashboard live sampling starts off. **Start live** samples the TV for 2 minutes and stops by itself; opening a component drawer takes one sample when process data is stale.
- CPU, network and paging rates restart after a gap of more than 60 seconds instead of reporting an average over the idle period.

## Source preview — 2026-10-11

- Minimal dark dashboard with English product copy and explicit app/process/startup states.
- Grouped component inventory with package/family boundaries and unknown-state handling.
- Redacted JSON diagnostic downloader and current platform/root status fields.
- Issue form, deterministic community report analysis and bot-comment workflow.
- Separate app-only and privileged integration packaging, with integration-boundary tests.
- Explicit signing credentials, original-code MIT license and upstream notices.
- Public installation/compatibility documentation with measured performance limitations.
- Private raw reports, device certificates and signed test packages excluded from the current tracked snapshot.

Vetro 0.2.0 is installed on the test TV. Dashboard contents, all 14 diagnostic sections and continued background operation after closing the app are verified. Unattended cold boot of this version remains to be tested. Private historical Git data is archived outside the fresh publication repository.
